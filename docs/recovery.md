# Recovery and removal

For a session test, stop supplying candidate guidance and start a fresh conversation without its attachment. This does not prove deletion of host-stored chat data.

For a project test, inspect actual instructions and files. Remove only Mini-owned changes within covered scope, preserve unrelated work, restore the observed backup if available and verify the result. Do not delete an entire project merely because it contains Mini.

For persistent-settings tests, restore the exact preserved prior text through the supported interface and read back the result where possible. Without observable prior state or a backup, identify the limit and prepare a concrete recovery proposal. Never invent successful restoration.

After interruption or lost acknowledgement, inspect current state against the intended change before another write. Record steps as not started, attempted, observed saved, failed or unknown. Resume only remaining covered work. Duplicate requests must not trigger blind duplicate mutations.

For missing or mismatched Operating content, reacquire the explicitly selected source. Do not choose a similarly named file, reconstruct from a summary or activate legacy memory instructions. Independent assistance remains available without a Mini runtime claim.

Repository changes are recoverable from the development branch and base commit. Published changes need distinguishable revisions; downloaded copies cannot be recalled. Supplied tools perform no release, account update or memory mutation.
