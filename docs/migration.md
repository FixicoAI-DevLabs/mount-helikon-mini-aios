# Migration from Mini 3.3

The six old memory bodies are legacy configuration. The candidate uses an explicitly selected JSON runtime and short System guidance. Old names and markers do not prove full-source access. The old install-package JSON is not the new runtime.

1. Inspect only relevant Mini-owned settings/records through available authorized mechanisms. Separate runtime instructions from personal preferences and useful project records.
2. Preserve accessible settings text and its observation scope. A prose export cannot promise exact restoration of host-synthesized memories.
3. Evaluate the candidate on an isolated surface first. Explicitly select its version. Residual legacy instructions remain historical data, not silently merged policy.
4. Resolve guidance conflicts and prepare a concrete replacement/recovery path before a production switch. Preparation does not authorize deleting unrelated memories or overwriting full Helikon.
5. Remove legacy configuration only after specific targets, intended losses, active dependencies and scope are resolved. No bulk memory-deletion script is included.
6. Verify actual saved settings where observable, exact source access in fresh/resumed chats, behavior with legacy residue, and recovery. Preserve failures and unknown states.

Legacy tokens and compulsory confidence/status footers are not supported Mini 4 interfaces. Express behavior in natural language. Optional continuity remains work data and is not automatically moved or converted to the full Helikon record schema.

The six original versioned files are preserved in `archive/3.3.0/`, alongside the historical `v3.3.0` tag. Mini 4.0.0 is the current repository release. This optional migration procedure has not been live-tested and is not part of the current release task.
